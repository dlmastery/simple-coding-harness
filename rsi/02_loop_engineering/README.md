# Repeat for a reason

[Course](../README.md)

A weak result invites another attempt. Repeating only helps when you know what to change, how to remember the current state, and when to stop.

Use the baseline and readable skill from the previous theme. Add feedback, state, and budgets one at a time.

| Lab | What changes |
|---|---|
| [02.01 · Let a failure motivate a second attempt](step_01_why_repeat/README.md) | A controlled comparison between a constant baseline and a calendar-based linear model. |
| [02.02 · Give the loop state and a budget](step_02_bounded_state/README.md) | A three-attempt loop with a current candidate, best candidate, ledger, and stopping rule. |
| [02.03 · Turn an error into a different action](step_03_use_feedback/README.md) | A feedback note that causes a documented change in the next experiment. |
| [02.04 · Stop repeated failure and oscillation](step_04_stop_the_loop/README.md) | A loop controller that stops on a repeated recipe, exhausted budget, or unchanged failure. |
| [02.05 · Resume without losing the experiment](step_05_resume/README.md) | A checkpoint and a resumed loop that retains candidate identities and spent budget. |
| [02.06 · Compare two ways to spend the same attempts](step_06_compare_loops/README.md) | A small comparison between fixed retries and feedback-guided revisions. |

Start with the first lab and follow its next link. Each lab uses a separate workspace and keeps its evidence. The agent writes code; you predict, inspect, and explain. [Skill entry point](../skills/rsi-tutor/SKILL.md).

A loop handles repeated work. It does not explain why a data failure and an expensive model should take different routes. That calls for a graph.
