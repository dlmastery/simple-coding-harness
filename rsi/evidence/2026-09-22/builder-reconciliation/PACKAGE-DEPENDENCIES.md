# The builder creates the package; the package still needs its dependencies

The historical bike and wine generation records name the same builder hash. This review recovered its exact bytes from Git commit 3dc2e5dbcaee0686fee766e19dc169638ee056dc and matched both brief and entry hashes. The author specialized a saved controller into two fixed-task wrappers. That is generation evidence; it does not show autonomous builder revision or general compilation of arbitrary briefs.

After generation, run.py imports lab and check_result from the specified course clone. It also needs the pinned task data, Python and its package dependencies. Its task, limit and recipe defaults live in the generated entry and task documents. It does not import or invoke the builder skill at runtime. The fresh bike execution in this walkthrough uses the copied entry without running the builder.

Removing the builder from the runtime path would leave those required task instructions intact. Removing the shared tool clone or its data would break this package. “The builder is no longer needed to run” does not mean “the package is standalone.” The copied README states the shared-tool dependency.

The copied run.py is byte-identical to the historical generated bike entry. Two added acceptance tools, check-evidence.py and check-request-state.py, are separately identified extensions in this walkthrough; they were not part of the older generated version. Neither trains a model. The initial checker compares expected identities; the second first reads current admission state. The agent supplies their syntax and invokes them under the readable course instructions.

No actual builder file was deleted and no independent agent was given an isolated package. Runtime source inspection and the recorded invocation establish the narrower dependency statement. This is a fresh output folder in the existing Python environment.
