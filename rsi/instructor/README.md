# Teaching guide

[Course](../README.md)

Start with a concrete failure. Ask students what they expect, run the experiment, and examine the result. A correct prediction without an explanation is not the whole outcome. A wrong prediction followed by a sound revised explanation can be strong progress.

## Use the checkpoints

| Point | Ask the student to explain |
|---|---|
| First baseline | What one prediction means and where the score came from |
| Fixed process | Which artifacts make the run repeatable |
| Loop | What feedback changed and why the loop stopped |
| Graph | Why a failure takes a particular route |
| Ontology | How a well-formed record can be scientifically invalid |
| System | Which fixed component contributes which capability |
| Meta-harness | The difference between builder and generated system |
| Self-* | What persists, what changes, and whether benefit was measured |
| Evidence | Which alternative explanation the comparison rules out |
| RSI | How an improver change reached later improvement work |

Ask quiz questions before revealing answers. Give hints that point to the experiment’s evidence. Do not reward memorizing filenames or paper titles.

## Assess a lab note

Score four criteria from 0–2: a testable prediction; an observed result with evidence; an explanation connecting mechanism and result; and a limit or transfer case. This is a local teaching rubric, not a validated psychometric scale.

Do not require every comparison to improve. An honest failed hypothesis with a good diagnosis is better work than an unsupported success claim. Separate implementation errors from conceptual misunderstandings.

## Set classroom scope

The sequence is a masterclass, not one lecture. For a short workshop, finish onboarding and one controlled model comparison. For a multi-session course, finish the foundation themes before selecting research studios. Do not skip the ontology and evidence bridge.

Record actual student completion times and confusing passages in a pilot. Current estimates come from authors, not learner trials. A tool walkthrough does not validate teaching effectiveness.

## Final portfolio

Require a task brief, data card, runnable harness, versioned skills, actual evidence, a failed experiment, cost record, claim audit, and teach-back. A peer should reproduce a small run from the handoff. For larger compute, require job and checkpoint evidence from the target backend.

Ask the student to explain why their experiment does or does not establish effective recursive improvement. Reserve acceleration claims for evidence across generations under comparable conditions.
